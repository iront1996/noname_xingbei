# M2 server-authority engineering guardrails

- Continue the existing M2 experiment only on its isolated `codex/v2-server-authority-m1` branch based on `feature/v2-connection-stability`; do not commit to or merge into that V2 base. After M2 validation, any V3 integration must use a separate isolated branch based on V3 and only with explicit user approval. Never commit directly to `master`, formal V2, or V3 production branches.
- Do not modify, deploy, restart, or stop VPS services, live V1/V2/V3 rooms, or monitoring center v2.3.0 without explicit user authorization.
- Formal V2 is permanently independent: do not modify, overwrite, protocol-bridge, or deploy changes to its live implementation. V3 and unrelated branches remain read-only unless the user explicitly authorizes a scoped change.
- The M2 core's final integration target is V3, not formal V2. After M2 validation, integrate only the necessary verified core through a separate isolated branch based on V3; never merge this whole V2-named experiment branch into V3. PR #1 targets a V2 base and must remain unmerged.
- Work in small, independently testable commits. Preserve V2-1 through V2-9 recovery and security tests; V2-10 remains paused.
- A simulated or local pass is not VPS compatibility, browser acceptance, real-player validation, or deployment approval. Record unverified boundaries explicitly.
- PR #1 targets `feature/v2-connection-stability` and must remain open/unmerged. A future V3 integration must use a separate V3-based PR; do not retarget or reuse PR #1.
- Final M2/V3 authority invariant: no human player, including the room creator or administrator, may be the game host or authoritative engine. Creation/administration permissions are control-plane capabilities only; they cannot execute rules, mutate authoritative game state, declare results, or control the managed host process. Any one player's disconnect must not close the room or stop its game process.
- Keep player transport loss separate from managed-host failure. Player disconnects use the uniform seat-recovery/timeout policy; managed-host crashes use the M4 checkpoint and recovery policy.
- Treat M1 `ownerResumeToken`, `resumeowner`, `room.owner`, `awaiting_host`, and `waiting_host_process` behavior as human-host compatibility only. Preserve it where useful, but do not make M2 or M3 depend on it and do not present it as the target architecture.
